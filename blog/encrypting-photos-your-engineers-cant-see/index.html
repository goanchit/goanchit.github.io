Encrypting photos so even your own engineers can't see them

September 8, 2026

Say you upload a photo on an app like Instagram. Somewhere there is a bucket that photo lands in, and somewhere there is an engineer with read access to that bucket — on-call, debugging a pipeline, whatever the reason. Could they open the file and look at it?

For most apps, yes. The photo is encrypted in transit (TLS) and usually at rest (SSE-S3, SSE-KMS, disk encryption), but the key used for at-rest encryption is one the platform holds and can produce on demand. Encryption at rest mostly protects against a stolen disk, not against someone who already has legitimate access to the systems that manage the key. If the IAM role that reads the bucket also implies decrypt access — and it usually does, because they are managed by the same team — then “encrypted at rest” and “readable by staff” are not in tension at all.

Making that untrue takes moving the encryption to the one place the company's infrastructure never touches: the user's device.

Envelope encryption, not one big key

The building block is envelope encryption[1]. Instead of encrypting every photo with one key that unlocks everything, each file gets its own randomly generated symmetric key — a data encryption key, or DEK — used once, with AES-256-GCM[2]. That key is then itself encrypted (“wrapped”) with a second key, the account's key-encryption key (KEK). The wrapped DEK is small, so it travels with the file's metadata instead of the file itself.

This split is what lets the two halves live in different places with different access patterns: the bucket only ever holds ciphertext, and the metadata store only ever holds wrapped keys. Neither one is useful without the other, and neither one is useful without the KEK.

Where the account key actually lives

The KEK is the load-bearing piece, and it has to never exist on a server in usable form. In practice it's derived on-device from something the user has — a password run through Argon2 or PBKDF2, or a keypair generated on first login and stored in the platform keychain (Keychain on iOS, Keystore on Android). Signal and WhatsApp both do a version of this for multi-device sync: a new device proves it belongs to the account, then receives the wrapped keys it needs re-wrapped for its own local key, without the server ever holding a usable copy in between[3].

Backups complicate this, because “forgot your password, lost your key, lost your photos forever” is not a product most companies will ship. WhatsApp's answer for chat backups is a 64-digit recovery key (or a password) stored in a hardware security module they say is deliberately built so that not even WhatsApp can extract keys from it in bulk — it only ever answers “does this guess unlock this one backup,” and locks itself after a handful of wrong tries[4]. That last mile — account recovery without a plaintext escape hatch — is the hardest part of this whole design, harder than the AES-GCM call.

Reading it back

Viewing the photo later runs the same trip in reverse. The device authenticates, asks the metadata store for the wrapped key and the bucket for the ciphertext, unwraps the key locally with the KEK it derives from the password, and decrypts. The server's job the whole time is just to check “is this account allowed to read this file id,” a question it can answer without ever seeing what's inside it.

What this buys you, and what it doesn't

This scheme genuinely stops the scenario at the top: an engineer, a compromised bucket credential, or a subpoena served on the storage provider alone all get back the same thing — opaque bytes and an opaque wrapped key, with the key that would open them sitting on a device the company never has access to.

It does not stop a compromised client, a malicious build the company itself ships to your device, or someone who gets you to unlock your own device. End-to-end encryption moves the trust boundary; it doesn't remove it.

And it costs you the server. Thumbnails, feed ranking, face grouping, content moderation classifiers — all of that currently runs on plaintext, server-side, at upload time. None of it can run there anymore if the server never has the plaintext. Real products handle this in one of a few ways: they don't apply full end-to-end encryption to the public feed at all (only to DMs or backups, where the audience is small and the server was never supposed to see the content anyway); they push the processing onto the device, encrypting the derived thumbnail alongside the original; or, for the one case regulators actually push on — CSAM detection — they attempt on-device perceptual hashing against a known-bad set before encryption, which is exactly the approach Apple proposed in 2021[5] and then shelved after enough people pointed out what a general-purpose on-device scanner could be repurposed into[6].

None of this is exotic cryptography. It's AES-GCM and a key hierarchy, the same primitives every KMS uses internally. What changes is a single design decision: where the unwrap happens. Move it off the server, and you've changed who has to trust whom.
